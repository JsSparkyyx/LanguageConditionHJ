### D1 DECISION (Yuxuan): bead violated-side magnitude vs γ
- **Setup.** A rule's h stays at h̄ until a violation k ticks ahead, then stays at h_v < 0. The
  target is y_t = (1 − γ)·h_t + γ·min(h_t, y_{t+1}). It gives V_k = h̄·(1 − γᵏ) + γᵏ·h_v.
- **Consequence.** V is negative only within k* ticks of the violation, where γ^k* = h̄ / (h̄ − h_v).
  With h̄ = 1 and one tick = 0.04 s:

  | h_v | k* at γ = 0.9 | k* at γ = 0.95 |
  |---|---|---|
  | −1 (old h, or ≥ 20 beads) | 6.6 ticks (0.26 s) | 13.5 ticks (0.54 s) |
  | −0.74 (10 beads) | 5.3 ticks (0.21 s) | 10.8 ticks (0.43 s) |
  | −0.5 (one bead) | 3.8 ticks (0.15 s) | 7.9 ticks (0.32 s) |

  A beads' 5 to 20 cm fall alone takes 0.1 to 0.2 s, so at −0.5 per bead the critic warns about when
  the first bead is already in the air.
- **Options:**
  - (a) Train on h_v = −1 whenever a bead rule is violated, and keep `particle_h` for metrics. To
    implement, relabel at load time in `LangSource`: `h_rules = −1` where `n_violating ≥ 1` for bead
    rules. `fails_soon` is unchanged because the sign is the same.
  - (b) γ = 0.95 (set `gamma` and `gamma_final`). The delay audit already flags every task at 0.4 s.
  - (c) Both.

## D. Data integrity, resume, jobs

### O1 [S1 risk] Two writers can append to one shard or ring
- **Where:**
  - `main/lang/workqueue.py:53-65` takes over a stale claim with `stat()` then `utime()`, which is
    not atomic;
  - `collect.cmd_shard` (`collect.py:405`) and `rounds.run_rounds` (`rounds.py:91`) hold no writer
    lock.
- **Problem:** two workers that see the same claim as stale both run the shard. The window is 90 s,
  and file-time caching on the shared disk makes it likelier. Both then append from the same head
  into the same memmaps.
- **Fix:**
  - Take over a stale claim by `os.rename(lock, <lock>.stale.<uuid>)`, then `mkdir`. Only one rename
    succeeds.
  - Writers hold an exclusive lock for their whole lifetime: `fcntl.flock` on `<root>/.writer.lock`,
    or an `O_EXCL` pid file with a heartbeat where flock is unreliable. Refuse to start if it is held.
- **One-off check:** for every shard and every `lang_episodes.jsonl` line, rows `[r0, r1)` must have
  `episode_id ==` the line's id and `t_in_ep == 0..n−1`. Report the shards that fail.

### O2 [S3] A rounds resume can be blocked by its own lockstep check
- **Where:** `main/lang/rounds.py:81-83` reopens the ring through `ItemSidecarBuffer.for_step_buffer`.
- **Problem:** that call raises when the two headers differ. A kill between `collect.py:298` and
  `:299` (the two flushes) produces exactly that, before the rollback at `rounds.py:121-126` can run.
- **Fix:** open `StepBuffer` and `ItemSidecarBuffer` directly, as `cmd_shard` does (`collect.py:428-430`).
  Then `discard_to(ring_n)` both, flush, and assert parity.

### O3 [S3] Ring capacity is fixed at the first launch
- **Where:** `main/lang/rounds.py:85`.
- **Problem:** resuming with a larger `--collect-rounds` or `--episodes-per-round` wraps the ring
  silently. The next resume then fails in `discard_to`.
- **Fix:** on reopen, check that the capacity covers the requested rounds, and refuse with a clear
  message if it does not.

### O4 [S3] A resume silently keeps the old switches
- **Where:** `main/lang/train.py:588-590` (`config_from_args`) loads `lang_config.json` whenever
  `--resume` is passed. The trainer writes that file before its first `state.pt`.
- **Problem:** if a first job dies early, relaunching with corrected `--no-*` flags runs the old
  configuration.
- **Fix:** reuse the saved config only when `state.pt` exists. Otherwise compare it with the CLI

### O5 [S3] Latent unit bug: filter margins are multiplied by h_scale
- **Where:** `LangConfig` inherits `h_scale = 20`, and `main/train/rollout.py:112-113` multiplies

## E. Evaluation methodology (new code in `eval_offline.py` / `eval_closed.py`)

### E1 [S1 for conclusions] The rank label is not what a γ = 0.9 critic learns
- **Where:** `envs/main/item_envs/item_buffer.py:369-382`. `fails_soon[t]` = h < 0 anywhere in ticks
  t … t + 24, including t itself (already-violated rows).
- **Problem:** by the formula in D1 with h̄ = 1 and h_v = −1, the ideal value of a violation k ticks
  ahead is 1 − 2·0.9ᵏ, which is 0.30 at k = 10 and 0.76 at k = 20. A correct critic therefore ranks
  such a harmful rule above a benign rule that sits at a low constant h (T3 `zone_include` ≈ 0.2,
  T6 containers near the stream). Near-chance referent scores (T1, T7) and T6's reversal can come
  from the label.
- **Add**, on the same pairs and per axis, task and consequence:
  - (a) `rank_acc_h`: rank by each rule's h_t, no model. This is a perfect reader with no foresight.
  - (b) Monte-Carlo discounted HJ return per (row, rule): y = h at the episode's last row, then
    y_t = (1 − γ)·h_t + γ·min(h_t, y_{t+1}) backward over `h_rules`.
    - `rank_acc_mc` = sign agreement of Q with y over pairs with |y₁ − y₂| > 0.05;
    - also report the Spearman correlation of Q vs y per state across its rules.
  - (c) Stratify every pair metric by the harmful rule's time to first violation: already violated
    (h_t < 0), 1 to 7 ticks, 8 to 25 ticks.
- **Docs:** `final_report.md` 5b says matching current h means "only the sentence can explain a Q
  difference". Both pair members share state and action, so that is always true. Matching h fixes
  the label, not the attribution. Reword it.
