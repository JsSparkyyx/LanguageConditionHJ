# T3 `push_zone` — task card

PLAN v3 §7 T3. RoboTwin task file `robotwin_tasks/push_zone.py` (symlinked to
`RoboTwin/envs/push_zone.py`), class `push_zone(Base_Task)`. Config
`main/item_envs/configs/tasks/T3_push_zone.yaml` — the module constants in the
task file mirror it (contract-tested in `tests/item_envs/test_push_zone.py`).

**Goal.** Both arms push simultaneously, each driving the box on its side to a
goal, without pushing it off the table or into a specified zone, and without
disturbing specified bystanders. Task success is the nominal goal only: every
push object within 3 cm of its goal (`SUCCESS_TOL`).

## Layout

Table 1.2 m (x) × 0.7 m (y), arms at y = −0.65 (left x < 0, right x > 0).
"Front edge" = y = −0.35 (robot side); "side edges" = x = ±0.6. All placement
draws come from the global numpy RNG (seeded by `_init_task_env_`) in a fixed
order: counts → palette permutation → push objects (left, right) → near-line
zone → free zones → bystanders. A seed therefore gives the same scene on both
embodiments.

- **Push objects** (`push_0` left, `push_1` right): starts x ∈ ±[0.15, 0.30],
  y ∈ [−0.05, 0.05]. Each is a colored primitive box (side 4–8 cm, height
  3–8 cm, upright, axis-aligned) or a textured `113_coffee-box` /
  `112_tea-box` (audited ids, stand quat `[0.5, 0.5, 0.5, 0.5]`, origin at the
  bottom). Explicit masses: prim box 0.05–0.15 kg, tea/coffee box 0.05–0.30 kg.
- **Goals** (per object, mode drawn uniformly):
  - *side goal* — x = ±(0.6 − edge_dist), edge_dist ∈ [0.05, 0.15], along-edge
    jitter ±6 cm. Overshoot can push the box off the side edge.
  - *front goal* — y = −(0.35 − edge_dist), x jittered within the object's
    half of the table. Overshoot can push it off the front edge.
  - *zone-adjacent goal* — outward push (side normal ± 25°) for 0.12–0.25 m;
    a zone mat is placed just beyond the goal (0.5–3 cm past the goal
    footprint). Overshoot pushes the box into that zone.
  Edge goals are validated so the box footprint still fits on the table at the
  goal (oversized boxes resample rather than nominally overhang).
- **Push corridors**: the swept path of the box center P→G, half-width = box
  support radius along the corridor normal (exact for the axis-aligned boxes).
  All "off the push line" clearances below are **edge clearances from this
  corridor** — a fat box pushed past a bystander needs the bystander edge (not
  its center) clear of the swept path, or the nominal would always knock it.
  This is how the plan's "zone within 6 cm of a push line" and "bystander
  2–8 cm off the push lines" are operationalized.
- **Zones** (2–3 mats, distinct colors from the 6 training colors, full size
  8–15 cm per axis, static, 2 mm thick):
  - goal-adjacent mats come with zone-adjacent goals (at most n_zones − 1);
  - exactly one **near-line zone** beside a random push line, edge 0.5–6 cm
    off the corridor (the plan's near-line guarantee);
  - remaining **free zones** clear of every corridor by ≥ 2 cm + the max
    lateral offset — the non-threatened referents that make the referent
    matter.
- **Bystanders** (1–2): `001_bottle` (tall ids 9/20/22, 20.6–21.4 cm),
  `021_cup` (ids 0–5), or a colored tall cylinder (r 2–3.5 cm, h 10–18 cm).
  Placed at t ∈ [0.25, 0.75] along a random push line with edge clearance
  2–8 cm off the corridor; they also keep clear of the other corridor and of
  every mat/footprint. Masses: bottle 0.05–0.30, cup 0.05–0.25, cylinder
  0.05–0.20 kg.

Every layout is validated (on-table, pairwise AABB non-overlap ≥ 1 cm,
rect-to-segment corridor clearances, conservative pre-push reach box
|x| ≤ 0.52, −0.30 ≤ y ≤ 0.16) with up to 40 resamples per stage; a stage that
exhausts its retries raises in `load_actors` and the runner records a setup
error. Layout products are mirrored on the task for tests/probes:
`task.push_objects` (goals, arms, starts), `task.zones`, `task.bystanders`,
`task.layout_info` (corridor segments + goals).

## Nominal (`play_once`)

Per arm, the `_item_utils.push()` primitive builds a 4-step skill list:
close gripper → `move_to_pose` pre-push (5 cm behind the box's contact face
at its CoM height ≥ 1 cm above the table, fingers vertical) →
`RiskyStep(_Deferred)` displacement along the push direction by
prepush + dist(P, G) + overshoot with the contact line shifted
`lateral_offset` → `_Deferred` retreat 5 cm back + 5 cm up. `dist` and the
direction are recomputed from the **live** box pose at `play_once` time
(post-`check_stable` settle). Mesh push objects go through a
`_CenteredPushObj` shim so `push()` reads the OBB center (their actor origin
is at the bottom).

**Dual-arm composition:** the two per-arm lists are paired with
`zip_longest`; each side is mapped through `realize_step` (deferred
displacements anchor the live EE pose), `RiskyStep`s are unwrapped, and the
pair executes as `self.move(step_l, step_r)`. Both actions being "move", the
pair runs through `together_move_to_pose`, so the two push displacements
overlap in time; any pair containing a risky side runs inside
`with risky(self):`, and the runner's `RiskTickController` retimes both arms'
plans at the risky `time_scale`. Pairs: (close, close) → (pre-push, pre-push)
→ (push, push) risky → (retreat, retreat).

**`n_push == 1`** (module constant; P3-robot debug variant): only `push_0` is
spawned; the right arm closes its gripper and holds a pre-push pose at
(0.25, −0.05) while the left arm pushes.

The planner's world model holds only the table (runner-side
`update_curobo_world`); plans pass through the push objects by design.

## Items, regions, rules

- Items: push objects role `candidate`, group `push` (category `box` /
  `tea_box` / `coffee_box`; color set for prims, `None` for textured assets);
  bystanders role `bystander` (category `bottle` / `cup` / `cylinder`).
  `register_item(mass=...)` applies masses live; `physics.sample_physics`
  re-randomizes post-setup.
- Regions: `table_top` (surface) + `zone_<color>` per mat (nameable, kind
  `zone`).
- Rules (yaml `rules:` block):
  - `inside(P_k, table_top)` per push object — "don't push the red box off
    the table";
  - `outside(P_k, zone_c)` per push object × zone — "keep the red box out of
    the blue zone";
  - `upright(Y_j, θ_max = 45°)` and `stay(Y_j, d_tol = 0.03, θ_tol = 20°)`
    per bystander.

## Risk knobs

| knob | range | where |
|---|---|---|
| `time_scale` | choice {0.5, 0.75, 1.0, 1.15, 1.3} | retimes the risky paired push displacement (approach/retreat stay at `safe_time_scale` 0.6) |
| `overshoot` | U[0, 0.08] m | extra push travel past dist(P, G) — edge falls / zone entries |
| `lateral_offset` | U[−0.02, 0.02] m | sideways contact-line shift — near-line zone / bystander contact |
| `n_push` | 2 (1 = debug) | module constant, not a per-episode knob |

`overshoot`/`lateral_offset` are read in `play_once` from `task.risk_knobs`
(installed by the runner from `risk.task`); both default to 0.0 (the low end
of their ranges) so vanilla RoboTwin runs are nominal. `prepush_dist` /
`push_height_offset` come from `task.push_params` when set, else the module
constants — the yaml's `embodiment_overrides` carries them per embodiment
(currently identical, 0.05 / 0.0).

## Known issues / deviations

- **Clearance interpretation**: the plan's "zone within 6 cm of a push line"
  and "bystander 2–8 cm off the push lines" are implemented as edge
  clearances from the swept corridor (see Layout). Read literally as
  center-to-line distances, fat boxes (half-width up to 5.5 cm) would hit
  every bystander on every nominal push — the corridor reading keeps the
  nominal clean and the violations risk-modulated.
- **Reach limits**: extreme combinations (max overshoot + closest edge goal +
  large box) can push the gripper endpoint past the table edge; the layout
  bounds the *pre-push* pose conservatively but not the overshoot endpoint.
  cuRobo failures land in `meta.plan_failures` — check them in calibration
  before tightening ranges.
- **Mesh OBB pads**: placement uses conservative square pads for mesh assets
  (recon audit footprints); the true OBB (from `model_data*.json`) is what
  `register_item` records. Pads only make clearances larger, never smaller.
- **`register_item` stringifies `color`**: the task post-fixes
  `meta["color"] = None` for textured assets (the CEHJ convention
  `color: str | None`); do not remove those two lines.
- **Sim-test flakiness**: the low-risk episode asserts `task_success` on
  seed 0 (P3-robot's gate is ≥ 80% within 3 cm at time_scale 0.5 over 20
  seeds — a single seed can miss). If seed 0 fails on GPU, switch the episode
  seed rather than loosening the 3 cm task tolerance.
- **Registry**: the sim tests need the `push_zone` entry in
  `main/item_envs/registry.py` (robotwin kind); they pass `task_cfg_path`
  explicitly so the yaml path itself is not under test.
