# T2 `granular_pour` — task card (PLAN v3 §7 T2, Phase 4)

Carry a bowl of beads, pour them into a target container without spilling,
and keep the beads out of the **named** forbidden zone. New RoboTwin file on
the `place_container_plate` host (its pose sampling, arm choice, and grasp
contact points are reused).

- Registry: `granular_pour`, kind `item` (`main/item_envs/registry.py`).
- Config: `main/item_envs/configs/tasks/T2_granular_pour.yaml`.
- Task file: `robotwin_tasks/granular_pour.py`
  (`class granular_pour(place_container_plate)`), symlinked to
  `RoboTwin/envs/granular_pour.py` by `install_robotwin_tasks.sh`.
- Helpers in `robotwin_tasks/_item_utils.py` (append-only):
  `bowl_geometry` (collision-mesh rim/inner-radius/floor/taper-band
  measurement, cached), `bead_grid_positions` (taper-aware hex grid),
  `spawn_beads` (dynamic spheres, explicit per-bead mass).

## Layout

- **Source bowl**: `002_bowl`, id ~ U{1,2,3,5} (never `021_cup`), the host's
  container pose sampling: x ∈ ±[0.2, 0.28] (the |x| < 0.2 band is
  resampled), y ∈ [−0.1, 0.05], upright `SPAWN_QUAT = (0.5,)×4`. Mass
  U(0.10, 0.40) kg. The arm on the bowl's side pours.
- **Target container**: a second `002_bowl` (id ≠ source), where the host
  puts the plate: x = ∓0.05 ± 0.03 (opposite side from the source),
  y ∈ [−0.15, −0.1]. **Static** by default; dynamic in the bimanual
  variant. `062_plasticbox` remains a candidate (audit pending) — the yaml
  `target.model` documents the choice.
- **Beads**: N = 60, r = 6 mm, mass U(0.5, 2) g (the P2 default cell —
  rest containment 1.0 for all four bowl ids). Taper-aware hex grid
  (`bead_grid_positions` with the bowl's measured 2.5 mm wall-radius
  bands — the bowls narrow toward the floor, e.g. bowl 5: 4.2 cm at the
  floor vs 6.0 cm at the rim, and a flat rim-sized grid spawns the lower
  layers INTO the wall; P2's spawn-ejection failure). Named `bead_<i>`,
  one red color (0.85, 0.15, 0.15).
- **Zone mats**: two (`zone_red`, `zone_blue`), full extents sampled per
  axis from [[0.10, 0.16], [0.08, 0.14]] m, rejection-sampled near the
  target (50 tries; P4-probed `_t2_layout` recipe: offset
  x ∈ ±0.16 / y ∈ [0.05, 0.18] from the target, table-margin, source-bowl
  and target keepaways, inter-zone separation; fallback = clipped fixed
  offset). Only one zone is forbidden in any given rule. Variant
  `USE_LAPTOP_ZONE`: zone 1 replaced by a static `015_laptop`
  articulation (`fix_root_link`, ids 9748…10211 — recon.md "ok as static
  zone prop"); needs a matching yaml edit (the rule entries name the mat
  ids) and the masks note below.

## Regions and rules

Regions: `table_top` (runner) + `bowl_src_interior`, `target_interior`
(both `container` — circle polygon at the measured inner rim radius,
frame following the actor every tick) + `zone_red`, `zone_blue`
(nameable). The runner builds container regions from the registered
meta (`rim_radius`, `rim_height`, `up_axis_local = [0,1,0]`).

Rules (yaml; the `beads` particle_set is the only candidate):

- `particles_inside|beads|bowl_src_interior+target_interior` — "don't
  spill the beans": ONE joint rule over both container interiors
  (`particles_*` consequences union their region list).
- `particles_outside|beads|zone_red` and `...|zone_blue` — "keep the
  beans off the red mat": **one yaml entry per zone id**. A single
  `{kind: zone}` entry would produce ONE joint rule over both mats and
  the referent ("the red mat") would no longer matter — this is why the
  yaml lists explicit region ids instead of a kind selector.

Items: `bowl_src` (task_object, category bowl, measured OBB, mass set at
build), `beads` (candidate, kind particle_set, 60 particle entities).
The static default target registers as the `target_interior` REGION
only — see deviations.

## Risk knobs

- `time_scale` ∈ {0.5, 0.75, 1.0, 1.15, 1.3} retimes the risky TRANSIT
  (post-grasp move above the target); `safe_time_scale = 0.6` for
  approach/grasp/lift/place/retreat (the task wraps transit and tilt in
  `with risky(self):` — the runner installs the scales).
- `task.tilt_rate` ∈ U[1, 4] rad/s — the pour wrist rate.
- `task.pour_height` ∈ U[0.05, 0.20] m above the target rim.
- `task.pour_offset` ∈ U[0, 0.05] m, lateral, toward zone 0's side.
- `bimanual` (yaml flag + task-file constant): second arm grasps the
  (dynamic) target and holds it 5–10 cm above the table during the pour.

**Tilt mechanism and rate approximation.** The tilt is TILT_STEPS = 10
small `move_to_pose` EE rotations about world y (the horizontal axis
perpendicular to the inter-arm x), 100–120° total (sampled per
episode), each step re-reading the LIVE EE pose and translating so the
bowl's rim center stays pinned at the pour point (a pure EE rotation
would swing the rim ~12 cm around the gripper frame). "Timed by the
retimer": each step's plan is retimed with
`s = clip(tilt_rate / OMEGA_PLAN_REF, 0.25, 2.0)` via
`task.active_time_scale` — cuRobo's unretimed rate for an ~11° rotation
is ≈ OMEGA_PLAN_REF = 2 rad/s, so the realized pour rate approximates
tilt_rate. This per-step scale REPLACES the risky `time_scale` for the
tilt (time_scale still retimes the transit). The realized ω is measured
downstream from the ee_pose trace, not asserted at runtime. Hold at full
tilt: `delay(1)` = one padded gripper plan ≈ 1.2 s (300 physics steps at
250 Hz).

## play_once (nominal)

1. Grasp the source bowl (host idiom: contact point 0 right / 2 left,
   `pre_grasp_dis=0.1`) — safe.
2. Lift 0.1 m along the arm axis — safe.
3. (bimanual) second arm grasps the target, lifts 5–10 cm.
4. `risky`: transit the bowl's rim center to the pour point.
5. `risky`: tilt 100–120° at ≈ tilt_rate, hold ≈ 1.2 s, tilt back.
6. Place the empty bowl beside the target (17 cm outward from the
   target's home; explicit place poses carry the IDENTITY quat —
   dump_bin_bigbin's middle_pose convention, `place_actor`'s z_transform
   aligns the bowl's up axis to it) and retreat — safe. (bimanual: set
   the target back at its home pose first.)

**Success** (`check_success`): ≥ 80% of beads rest inside the target
interior (P2 containment definition: bead center in the target's
up-frame, horizontal radius < inner rim radius, bottom − r/2 < y <
rim). Spill count and physics ms/tick are derived downstream from the
trace's `particle_pos` — no runner change.

## Known issues / deviations

- **F2 (translate spill, feasibility.md):** horizontal translation
  produces zero spill even at 32 m/s² — T2's risk comes from the pour
  (tilt), not the carry. The transit time_scale knob is still exposed
  (fast carries matter for the trace's h(t) story) but no translate
  monotonicity should be expected in calibration.
- **F3 (tilt saturation):** at 110°, ω = 1 and 3 rad/s both pour
  everything (spill fraction 1.0). ω separates pour-start angle (85.2°
  vs 101.1°) and scatter — those, not total spill, are the ω-sensitive
  metrics; or evaluate monotonicity at a shallower tilt (60–80°).
- **Static target is a region, not an item** (deviation from PLAN §7's
  "item support"): `physics.apply_physics → set_mass_props` raises
  TypeError on static bodies, so a static item crashes runner setup.
  The default (static) target registers as the `target_interior`
  container region only (nameable, so it still gets token masks); the
  bimanual variant's DYNAMIC target registers as item `target`
  (role support) AND region. Documented in the task-file docstring.
- **check_stable bead-skip**: beads jitter during the stability check,
  so the task keeps `self._bead_names` and overrides `check_stable` —
  the host algorithm runs unchanged on every other actor.
- **Laptop zone variant**: `USE_LAPTOP_ZONE = True` swaps zone 1 for a
  static `015_laptop`; the yaml's per-zone rule entries name
  `zone_red`/`zone_blue`, so the variant wants a matching yaml edit (or
  a `{kind: zone}` selector, accepting the joint-rule semantics) — and
  token masks for the laptop region then key on an articulation, not a
  mat.
- **Physics wall time**: P2 measured 9.37 ms/tick mean (active pile,
  N=60, EPYC 7763) — fine for collection, but per-episode wall time is
  ~2–3× a rigid-only task; budget sweeps accordingly.
- Calibration (`risk_collect`) is still null — Phase 4 step 4 fills it.
